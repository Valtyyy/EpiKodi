# Spike 2.1 : composition vidéo (webview transparent sur `GtkGLArea` libmpv)

Issue #10. Code : `spikes/video-overlay/` (crate autonome, `[workspace]` vide). Référence : ARCHITECTURE.md §5.1 et §5.2 (risque n°1). Les chiffres ci-dessous proviennent tous de `spikes/video-overlay/target/logs/*.json` (non versionnés), produits par `run-measure.sh` et résumés par `summarize.py`. Rien n'est estimé.

## Verdict court

**Plan A (GtkOverlay { GtkGLArea, WebView transparent }) fonctionne avec Tauri 2 sur AMD (Wayland et XWayland)**, sans contournement de Tauri. Le focus clavier reste dans le webview, aucune erreur GL, pas de plantage sur 10 aller-retours plein écran. Deux réserves : (1) le seuil « < 1 % d'images perdues » n'est tenu qu'en régime établi (0 perte hors démarrage et transitions plein écran), pas sur la fenêtre totale de 30 s ; (2) l'overlay coûte environ **+10 points de CPU** (un cœur) par rapport au plan B. Intel et NVIDIA ne sont pas mesurés. Recommandation : **retenir le plan A, garder le plan B (déjà fonctionnel, même code de rendu) comme repli**, voir la dernière section.

## Contexte et hypothèse testée

ARCHITECTURE.md §5.2 : « aucune source confirmant un WebKitGTK transparent par-dessus une `GtkGLArea` ». L'hypothèse est maintenant confirmée sur cette machine : le webview Tauri (`wry` 0.57.1, `webkit2gtk` 2.0.2) est retiré du `default_vbox()` puis ré-inséré comme enfant overlay d'un `GtkOverlay` dont l'enfant principal est la `GtkGLArea`.

## Réalisation

- **Plan A** : `setup` crée la fenêtre (`WebviewWindowBuilder`, `.transparent(true)`), récupère `window.gtk_window()` et `window.default_vbox()`, retrouve le `WebKitWebView` parmi les enfants du vbox (pas besoin de `with_webview`), le retire, applique `set_background_color(RGBA 0,0,0,0)`, puis `Overlay { GLArea, WebView }` est packé dans le vbox. Les événements ne traversent pas l'overlay (`set_overlay_pass_through(false)`), le webview reçoit donc clavier et souris.
- **Respect de §5.1** : `LC_NUMERIC=C` rétabli après l'init GTK et avant `mpv_create` ; configuration fermée (`config=no`, `load-scripts=no`, `ytdl=no`, `input-default-bindings=no`, `input-vo-keyboard=no`, `osc=no`), `vo=libmpv` ; le contexte de rendu est créé dans le handler `realize` de la `GLArea`, contexte GL courant, **avant** `loadfile` (si la surface n'est pas encore réalisée, le fichier est mis en attente et chargé par `realize`) ; `get_proc_address` via `eglGetProcAddress` (Wayland) ou `glXGetProcAddressARB` (X11) avec repli `dlsym` ; le callback de mise à jour mpv ne fait que poser un drapeau atomique et envoyer un message au fil GTK, qui appelle `queue_render` ; le rendu cible le FBO lié (`GL_FRAMEBUFFER_BINDING` interrogé à chaque `render`). Les pointeurs `wl_display` / `Display*` sont aussi transmis à mpv (nécessaire à l'interop VAAPI zéro-copie).
- **Plan B** (`--plan b`) : `GtkStack { "ui" = webview, "video" = GLArea }`. La page vidéo est affichée à la lecture ; les touches GTK (`key-press-event` de la fenêtre) sont relayées à mpv (Espace pause, flèches seek, `f` plein écran, Échap retour) et l'information passe par `show-text`. Le texte de l'OSD est formaté côté Rust : `show-text` appelé via `libmpv2::Mpv::command` n'a pas développé les `${propriété}` (la première capture affichait `${time-pos}` littéralement).
- **Mesure** (`--measure [--duration N]`) : échantillon chaque seconde de `frame-drop-count`, `decoder-frame-drop-count`, `estimated-frame-number`, `hwdec-current`, CPU (`/proc/self/stat`) et RSS ; 5 touches synthétiques injectées dans la boucle GTK (plan A, à t=2 s) ; 10 cycles plein écran / fenêtré (20 bascules, 750 ms d'intervalle, à partir de t=6 s) ; `glGetError` après chaque rendu ; JSON final puis sortie.

## Protocole

Chaque run : `./run-measure.sh <nom> [VAR=val] -- [args]`, 30 s de lecture, `timeout 120`, sortie redirigée dans `target/logs/`. Pourcentage d'images perdues = `frame-drop-count / estimated-frame-number`. « Régime établi » = intervalle t=2..5 s et intervalle après la dernière bascule (t=22..30 s). Le CPU est exprimé en % d'un cœur (100 % = un cœur complet), moyenne des secondes 2 à 5. Le run « sans webview » (`--no-overlay`) cache le webview et sert de référence pour le coût de l'overlay.

Limite connue de l'instrument : les captures sont prises à t=4 s (fenêtré) et pendant les bascules (plein écran) en dessinant l'arbre de widgets GTK, ce qui interrompt le rendu une fraction de seconde. L'unique perte observée entre t=2 s et t=5 s dans presque tous les runs est très probablement due à cette capture (non démontré : à vérifier en relançant sans `--screenshots`).

Notes de lecture :

- Pertes décodeur : `decoder-frame-drop-count` = 0 dans tous les runs.
- Le total hors régime établi se concentre au démarrage (première seconde) et pendant les bascules plein écran. Démarrage, plan A Wayland : 19 pertes sur 31 images dans le premier run à froid (`a-wayland`, qui explique les 2,62 %), puis 0 à 2 sur les runs suivants. Pendant les bascules (t=5..22 s) : 4 à 5 pertes sur ~520 images (0,77 à 0,97 %) en plan A Wayland, contre 4 sur 519 sans webview.
- Référence sans webview (Wayland, 2 runs) : 0,55 % et 0,54 % au total, CPU 16,0 et 16,6 %. Le coût mesuré de l'overlay est donc d'environ **+9 à +10 points de CPU** (26 contre 16-17 %) pour environ 0,1 à 0,4 point d'images perdues en plus. Le plan B a le même CPU que « sans webview », ce qui est cohérent : le webview n'est plus dessiné pendant la lecture.
- X11 (XWayland) : mpv n'obtient que `vaapi-copy` (le plan A Wayland obtient `vaapi` zéro-copie), sans surcoût CPU visible dans ces mesures (27 contre 26 %). Le nombre d'images totales y est plus bas (812 à 889 contre 913 à 922) parce que la lecture démarre plus tard dans la fenêtre de 30 s (17 images au premier échantillon contre 31).
- Dérive RSS : la hausse (≈ +16 Mo) survient pendant les bascules puis reste plate (294 028 kB après les bascules, 294 036 kB à la fin sur le run final), et elle est identique sans webview (+16 Mo). Elle ne prouve ni l'absence ni la présence d'une fuite GL sur la durée : 30 s ne suffisent pas. Voir la checklist.
- Désactiver le moteur DMABUF de WebKit n'a pas changé le fonctionnement ici (pas d'écran noir avec ou sans) mais a coûté environ +5 points de CPU sur un run : ne l'activer qu'en cas d'écran noir (typiquement NVIDIA).
- Dispersion : les runs répétés sont peu nombreux (1 à 4 par configuration) ; les pourcentages de pertes reposent sur 5 à 25 images perdues, donc de quelques unités de granularité. Ne pas sur-interpréter l'écart Wayland / X11.

## Problèmes rencontrés

1. **Pas d'écran noir ni de désynchronisation** observés sur AMD, avec ou sans `WEBKIT_DISABLE_DMABUF_RENDERER=1`. Le risque NVIDIA décrit au §5.2 n'est pas testé.
2. **`Gdk-CRITICAL: gdk_wayland_display_get_wl_display`** sous `GDK_BACKEND=x11` : mon code appelait la fonction Wayland sur un display X11. Corrigé (le pointeur n'est demandé que pour le backend actif) ; vérifié par un run X11 sans CRITICAL.
3. **`Cannot load libcuda.so.1`** en tête de chaque log : message de sondage matériel de mpv/ffmpeg, sans conséquence ici (pas de NVIDIA).
4. **`show-text` ne développe pas `${...}`** via `libmpv2::Mpv::command` : le texte d'OSD du plan B doit être formaté côté Rust (fait).
5. **WebKit throttle un webview caché** : en plan B, la page JS tourne à ~3 ticks/s tant que la page vidéo est affichée (`ticks` : 86 après 30 s contre 581 en plan A pour un minuteur de 50 ms). Sans conséquence pour le plan B, mais à retenir si un état était poussé par le webview pendant la lecture.
6. **API dépréciée** : `glib::MainContext::channel` (utilisé pour le rendu planifié et le démarrage) est déprécié dans glib 0.18 mais reste l'idiome pour la paire gtk/glib 0.18 de Tauri 2.12. Les avertissements sont masqués par `#![allow(deprecated)]` ; `cargo clippy` est sans avertissement.
7. **Instrumentation** : les captures interrompent brièvement le rendu (voir Protocole). Des tests de performance à venir devraient désactiver `--screenshots`.

Aucun contournement de Tauri n'a été nécessaire : `gtk_window()`, `default_vbox()` et le parcours des enfants du vbox suffisent ; `wry`/`webkit2gtk` directs n'ont pas été utilisés.

## Recommandation

**Plan A**, sous réserve de la checklist ci-dessous.

Justification : l'hypothèse de transparence est confirmée sans écart par rapport à Tauri ; le focus clavier reste dans le webview ; aucune erreur GL ; les pertes d'images en régime établi sont nulles ; les contrôles HTML (focus, barre de progression JS) restent possibles pendant la lecture, ce qui est le besoin produit. Le coût est un CPU supérieur d'environ 10 points de cœur sur cette machine (webview redessiné à 20 Hz par le test, ce qui est un pire cas), et des pertes un peu plus nombreuses au démarrage et pendant les bascules plein écran.

Repli : **plan B**, déjà fonctionnel et mesuré dans ce spike (CPU 16,6 à 17,3 % en Wayland, 0,66 à 0,88 % de pertes au total). Il réutilise la même `GtkGLArea` et le même code de rendu ; seul le conteneur (`GtkStack` au lieu de `GtkOverlay`) et le relais clavier changent. Déclencher le repli si l'un des cas suivants se confirme sur un autre GPU : contrôles invisibles ou fond opaque, écran noir non résolu par `WEBKIT_DISABLE_DMABUF_RENDERER=1`, focus clavier perdu, pertes d'images régulières en régime établi. Pour la bascule à l'exécution, prévoir l'option dès la racine de composition (un drapeau de configuration) plutôt qu'une décision à la compilation.

Pour l'ADR-002 : décision « Plan A retenu sur AMD Wayland/XWayland, validation Intel/NVIDIA et confirmation visuelle en attente ».

## À confirmer manuellement

Non mesuré / non vérifiable par l'agent :

1. **Aspect à l'écran** (plan A, Wayland puis X11) : `cd spikes/video-overlay && cargo run`, puis `GDK_BACKEND=x11 cargo run`. Vérifier : barre de contrôles et journal de touches nets, vidéo visible à travers, pas de clignotement, de bordure noire ni de déchirure, y compris en plein écran (agrandir la fenêtre, ou lancer `--measure` et regarder les bascules).
2. **Clavier physique** : cliquer dans la fenêtre puis taper ; le journal `keys:` doit se remplir pendant la lecture, Tab doit déplacer le focus entre les boutons. Le test automatisé n'a injecté que des événements GTK synthétiques.
3. **Souris** : survol et clic des boutons pendant la lecture (le clic sur « Play » en plan B lance la lecture).
4. **Fuite GL / mémoire** : lancer 100 bascules plein écran (changer `CYCLES` dans `src/main.rs`, ou lancer `--measure --duration 300` après avoir porté `CYCLES` à 100) et comparer `rss_kb_after_toggles` et `rss_kb_end` ; surveiller `glGetError` (champ `gl_errors`).
5. **Autres GPU** (non mesurés) : Intel (Mesa i965/iris, `vaapi`) et NVIDIA (pilote propriétaire, `nvdec`/`vdpau`, risque d'écran noir avec le moteur DMABUF de WebKit). Procédure identique pour chaque machine : installer les prérequis du README, générer la vidéo de test, puis
   `./run-measure.sh a-wayland --`, `./run-measure.sh a-x11 GDK_BACKEND=x11 --`, `./run-measure.sh a-wayland-nodmabuf WEBKIT_DISABLE_DMABUF_RENDERER=1 --`, `./run-measure.sh b-wayland -- --plan b`, `./run-measure.sh a-wayland-nooverlay -- --no-overlay`, puis `python3 summarize.py` et lire `hwdec_current` (sur NVIDIA, un `no` indique un décodage logiciel). Répéter chaque run au moins trois fois ; le premier lancement à froid perd davantage d'images.
6. **Session X11 native** : les runs « X11 » passent par XWayland. Un test sous une vraie session X11 (GLX natif) reste à faire.
7. **Mise à l'échelle HiDPI** (`scale_factor` > 1) : le rendu multiplie déjà la taille de la `GLArea` par le facteur d'échelle, non testé ici.
