# Spike 2.5 - Orca / AT-SPI sur une page Tauri (WebKitGTK) (issue #14)

Code et scripts : `spikes/orca/` (voir son `README.md` pour tout rejouer). Journaux bruts : `spikes/orca/target/logs/`.

Statut : la partie AT-SPI est mesuree. L'ecoute reelle d'Orca n'a pas ete faite (elle demande un humain) : tout ce qui concerne ce qu'on entend est marque **a confirmer manuellement**.

## 2. Protocole de mesure

1. `spikes/orca/dist/index.html` est la page de test. Le script interne fait le scenario sans humain : focus sur "Films" puis "Series" (fleches simulees) a 0 s et 2 s, clic sur "Series" a 4 s (annonce assertive), ouverture puis fermeture du dialogue a 6 s et 9 s, progression 60 % puis 100 %, saisie "test" dans le champ, retour sur "Accueil". Le cycle se repete toutes les 16 s.
2. `spikes/orca/scripts/atspi_probe.py` :
   - `Atspi.init()` puis recherche de la fenetre dont le nom est "Orca spike" dans le bureau AT-SPI ;
   - dump de l'arbre (role, nom, etats, attributs DOM exposes par WebKit, lecture de `Value` et `Text`) ;
   - `Atspi.EventListener.new(...)` puis `register` de `object:state-changed:focused`, `object:text-changed:insert`, `object:children-changed`, `object:announcement` (les 4 sont enregistres avec succes : `True`) ;
   - ecoute de 35 s, filtre des evenements dont la source appartient a `orca-spike` (les evenements du terminal qui lance la sonde sont comptes, pas affiches) ;
   - `deregister` de chaque evenement, `Atspi.exit()`, sortie a code 0.
3. Variante `--all-object-events` : enregistre la famille entiere `object` pour verifier s'il part un evenement quelconque des regions live.

Commandes executees (sorties dans `spikes/orca/target/logs/`) :

| Journal | Contenu |
|---|---|
| `probe-run2.log` | sonde standard, 35 s, avec dump de l'arbre au debut et a la fin |
| `probe-run3-all-object.log` | sonde `--all-object-events`, 35 s |

Le premier essai (`probe-run1.log`) a ete fait avant l'ajout des attributs et du filtre par application ; il n'est pas utilise ici.

Les lignes du terminal (`source.role='terminal'`) : 50 a 140 evenements non lies a l'app selon l'execution, correctement ecartes par le filtre.

## 4. Evenements des regions live

| Evenement | Enregistre ? | Observe pendant l'ecoute (35 s) | Verdict |
|---|---|---|---|
| `object:text-changed:insert` sur la region polie | oui | 0 (les 2 observes viennent du champ de recherche) | **Non observe** |
| `object:text-changed:insert` sur la region assertive | oui | 0 | **Non observe** |
| `object:children-changed` sur les regions | oui | 0 (les `children-changed` concernent le dialogue et le document) | **Non observe** |
| `object:announcement` | oui (`register` renvoie `True`) | 0 | **Non observe** |
| Toute famille `object:*` (sonde `--all-object-events`) | oui | aucun evenement dont la source est une region live (compteur `LIVE` = 0) | **Non observe** |

Lecture : WebKitGTK expose bien les attributs `live=polite` / `live=assertive` et met a jour le texte des regions (le texte est lisible a chaque dump, avec le contenu courant), mais **aucun evenement AT-SPI n'est emis lors de ces changements** pendant 35 s, et `object:announcement` n'est jamais emis.

Consequence pour Orca : tout ce qui depend d'un evenement (focus, dialogue, saisie, progression) est transmis ; tout ce qui n'est annonce que par une region live pourrait ne pas etre lu. **A confirmer manuellement** (checklist section 7, points e et f).

## 5. Evaluation de l'Announcer

Code : `spikes/orca/announcer/src/lib.rs`. Trait `Announcer::announce(&self, text, priority)`, implementations `NoopAnnouncer` (les regions `aria-live` sont le canal) et `SpeechDispatcherAnnouncer` (un sous-processus `spd-say -N orca-spike -P <important|message> -- <texte>`, attente de la fin du processus, comptage des echecs).

Tests unitaires : `cargo test` = 4 tests OK (`announcer/` : mapping des priorites, Noop, echec compte sans panique, succes compte 0). Journal : `announcer-test.log`.

Latence (`bench-silent.log`, 100 appels par ligne, sauf Noop) :

| Chemin | p50 | p95 | max | Commentaire |
|---|---|---|---|---|
| `NoopAnnouncer::announce` (100 000 appels) | 0.000 ms | 0.000 ms | 0.006 ms | appel de trait seul |
| `SpeechDispatcherAnnouncer`, programme `/bin/true` | 0.790 ms | 1.190 ms | 1.457 ms | cout du sous-processus seul (sans IPC ni audio) |
| `spd-say -S` (arrete la parole, pas de son) | 1.999 ms | 2.228 ms | 2.625 ms | IPC reel avec speech-dispatcher, mesure hors trait |

Un seul appel audible a ete fait : `bench --speak-once "Test Orca spike"` (journal `speak-once.log`) : `announce()` a rendu la main en 4.083 ms, `failures=0`. **Que le son ait ete entendu : a confirmer manuellement.** Aucun autre appel audible n'a ete fait.

Limites et points ouverts :
- Latence du fallback : quelques ms, largement sous le seuil de perception ; le cout d'un appel est negligeable face a la synthese.
- Le fallback est aujourd'hui un processus par message. Un client persistant (crate `speech-dispatcher` ou socket) est plus propre, mais impose `libspeechd`.
- Priorite assertive : `important` ne coupe pas forcement la parole en cours ; une annulation (`spd-say -C`) n'a pas ete testee.
- Double annonce : si Orca lit deja les regions, le fallback doublerait l'annonce. Le fallback doit donc etre active seulement si l'ecoute manuelle confirme l'absence d'annonce d'Orca.

## 6. Verdict provisoire

- **Orca suffit** pour la navigation et les elements exposes avec un evenement : roles, noms, focus du roving tabindex, dialogue (nom et apparition), champ de saisie, image (alt), valeur de progression. Ces elements sont vus par AT-SPI sans ambiguite. **A confirmer a l'ecoute.**
- **Orca ne suffit probablement pas** pour les annonces asynchrones des regions `aria-live` (minuteur "Lecture : N s", annonce assertive apres clic) : aucun evenement AT-SPI n'est emis (section 4). **Un fallback `speech-dispatcher` est necessaire pour ces annonces**, sauf si l'ecoute manuelle montre qu'Orca les lit malgre tout.
- Par consequent, la decision ne doit pas bloquer l'interface : le port `Announcer` est prevu, et le fallback peut etre branche sur les messages d'etat (annonces de changement de page, de confirmation) sans toucher a la navigation.

Ce verdict reste provisoire tant que la checklist de la section 7 n'a pas ete jouee par un humain.
