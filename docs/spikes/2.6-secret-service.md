# Spike 2.6 : Secret Service (trousseau) pour la clé TMDB

- **Issue :** #15
- **Code :** `spikes/secret-service/` (crate autonome, `[workspace]` vide)
- **Sortie brute des scénarios :** commande `spikes/secret-service/scripts/run-all.sh` (copie en annexe)
- **Statut :** scénarios automatisables exécutés ; les points restants sont marqués « à confirmer manuellement »

## 1. Question

ARCHITECTURE.md §9 impose une clé TMDB en écriture seule, stockée dans le trousseau, avec la variable d'environnement `OPEN_MOSAIK_TMDB_API_KEY` comme repli verrouillé. Ce spike vérifie, sur Linux avec GNOME Keyring :

1. que `keyring` lit, écrit et supprime une entrée ;
2. le comportement sans Secret Service ;
3. le comportement d'un trousseau verrouillé, et si un appel reste bloqué sur une invite de déverrouillage ;
4. que le repli par variable d'environnement fonctionne dans tous les cas.

## 3. Choix du backend

`keyring` 3 propose plusieurs backends Linux. Le spike utilise **`sync-secret-service` seul**.

- **Persistance.** La documentation de `keyring` (`src/keyutils_persistent.rs`) indique que le cache keyutils ne survit pas au redémarrage ; c'est le Secret Service qui assure la persistance. `linux-native-sync-persistent` ajouterait une seconde copie du secret dans le keyring noyau, sans bénéfice pour une application de bureau qui relit la clé à chaque démarrage.
- **Synchrone.** Le README de `keyring` précise que l'accès au trousseau est toujours synchrone. Une variante `async-secret-service` n'apporterait rien ici.
- **Chiffrement du transport.** Sans les features `crypto-rust` ou `crypto-openssl`, `keyring` utilise `EncryptionType::Plain` (`src/secret_service.rs`, l. 141-143). Le secret circule donc **en clair sur le bus de session**. Voir la recommandation 8.

## 4. Protocole observé

Le protocole est la spécification freedesktop « Secret Service » sur le bus de session D-Bus :

- service `org.freedesktop.secrets`, objet `/org/freedesktop/secrets` (interface `org.freedesktop.Secret.Service`) ;
- collection `/org/freedesktop/secrets/collection/login` (interface `org.freedesktop.Secret.Collection`, propriété `Locked`) ;
- invite `/org/freedesktop/secrets/prompt/...` (interface `org.freedesktop.Secret.Prompt`, méthode `Prompt`, signal `Completed`).

Appels observés dans les journaux du faux service (scénario 4) : `Service.OpenSession`, `Service.ReadAlias("default")`, `Properties.Get(Collection, "Locked")`, `Service.SearchItems`, `Service.Unlock`, `Prompt.Prompt`. Le scénario 3 utilise en plus `Service.Lock` (envoyé par le spike via `dbus-send`).

Deux limites de la crate, lues dans les sources :

- **Délai court par appel.** `dbus-secret-service-4.1.0/src/proxy/mod.rs` l. 17 fixe `Duration::from_millis(2000)` pour chaque appel au service. Un service qui ne répond pas échoue donc au bout de 2 s.
- **Attente d'invite sans borne.** `dbus-secret-service-4.1.0/src/prompt.rs` attend `Completed` en boucle, pendant `ONE_YEAR_SECONDS` par défaut. `keyring` 3.6.3 appelle `SecretService::connect` sans `connect_with_max_prompt_timeout` (`secret_service.rs` l. 144 et 337). **Un appel qui déclenche une invite sans réponse peut donc bloquer très longtemps.** C'est pourquoi le spike encadre chaque appel par un délai (`--timeout-secs`, 8 s par défaut) et interroge l'état de verrouillage avant tout accès (garde).

## 5. Ce que fait le spike

- `set <valeur>`, `get`, `delete` : entrée de test `open-mosaik-spike` / `tmdb-api-key-spike`. Toute commande qui touche une entrée vérifie d'abord `Locked` (lecture seule) et renvoie `Trousseau verrouillé` (code 4) sans déclencher d'invite.
- `status` : état de la collection par défaut, puis accès à l'entrée.
- `resolve` : ordre `OPEN_MOSAIK_TMDB_API_KEY` (« verrouillé par l'environnement ») > trousseau > « non configurée ». La valeur n'est jamais affichée.
- `raw-get` : **diagnostic uniquement**, appelle `get_password` sans la garde, pour observer le comportement brut de `keyring`.
- Erreurs : `NoStorageAccess`, `PlatformFailure`, `NoEntry` et autres sont traduites en français et commencent par `Trousseau indisponible : ` (sauf « Aucune valeur enregistrée »).
- Codes de sortie : 0 succès, 1 trousseau indisponible ou erreur, 2 usage, 3 non configurée (`resolve`), 4 verrouillé.

Point corrigé pendant le spike : la garde convertissait les erreurs D-Bus en `NoStorageAccess` (« accès refusé ou impossible »), alors que `keyring` les rapporte en `PlatformFailure` (« erreur de la plateforme ») sur son propre chemin. Les deux messages décrivaient la même cause. La garde utilise désormais `PlatformFailure`. `NoStorageAccess` reste réservé aux refus, par exemple une invite fermée (`unlock prompt was dismissed`).

### Scénario 3 : trousseau verrouillé (bus isolé, mot de passe de test)

Déroulé (`scripts/scenario-locked.sh`, dans un bus isolé) :

- **A.** `gnome-keyring-daemon --unlock` avec un mot de passe de test (`echo testpw |`, seulement dans le bus isolé) crée le trousseau de connexion. Le spike y écrit l'entrée de test.
- **B.** `org.freedesktop.Secret.Service.Lock` sur la collection `login`.
- **C.** arrêt du démon par son PID, puis redémarrage **sans** `--unlock`. C'est l'état d'un démarrage sans mot de passe déverrouillé.

| Étape | Commande | stdout (copié) | Code | Durée |
|---|---|---|---|---|
| B | `status` | `Trousseau verrouillé : déverrouillez le trousseau de la session, puis réessayez` | 4 | 7 ms |
| B | `get` | (même message) | 4 | 7 ms |
| B | `resolve` | `TMDB : Trousseau verrouillé : déverrouillez le trousseau de la session, puis réessayez` | 4 | 7 ms |
| B | `raw-get` (sans garde) | `Trousseau indisponible : accès refusé ou impossible (Secret Service: unlock prompt was dismissed)` | 1 | 9 ms |
| B | `resolve` avec env | `TMDB : configurée (source : environnement, verrouillé par l'environnement)` | 0 | 6 ms |
| C | `status` | `Trousseau verrouillé : …` | 4 | 9 ms |
| C | `set autre-valeur` | `Trousseau verrouillé : …` (aucune écriture) | 4 | 7 ms |
| C | `raw-get` | `… unlock prompt was dismissed)` | 1 | 9 ms |
| C | `resolve` avec env | `TMDB : configurée (source : environnement, verrouillé par l'environnement)` | 0 | 6 ms |

Lecture :

- **Pas de blocage** dans ce scénario : le bus isolé n'a aucun greeter ni aucune invite graphique. L'invite est donc refusée immédiatement (`unlock prompt was dismissed`). Sur un bureau réel, une invite serait affichée et l'appel attendrait sa réponse. **Non observé ici : à confirmer manuellement** (procédure en section 8).
- La garde évite tout appel qui déclencherait `Unlock`. Le faux service du scénario 4 montre que `status` ne reçoit que `OpenSession`, `ReadAlias` et `Properties.Get(Locked)`, sans `Unlock`.
- **Démarrage automatique (autologin).** Le démarrage sans mot de passe n'a pas été reproduit (il dépend de PAM). Le scénario C montre seulement qu'un trousseau protégé par mot de passe reste verrouillé quand le démon démarre sans l'avoir déverrouillé. **Le comportement réel avec autologin : à confirmer manuellement** (section 8).

### Scénario 4 : service qui ne répond pas (doubles de test, bus isolé)

`scripts/fake-secrets.py` simule un service `org.freedesktop.secrets` inexistant en production. Il journalise chaque appel reçu.

**Mode `silent`** : `OpenSession`, premier appel de `connect`, ne répond jamais.

| Commande | stdout (copié) | Code | Durée |
|---|---|---|---|
| `status` | `Trousseau indisponible : erreur de la plateforme (DBus error: Did not receive a reply. Possible causes include: …)` | 1 | 2019 ms |
| `--timeout-secs 3 resolve` | même message | 1 | 2011 ms |
| `resolve` avec env | `TMDB : configurée (source : environnement, verrouillé par l'environnement)` | 0 | 8 ms |

Le délai effectif est celui de la crate (2 s, section 4), pas celui du spike : `--timeout-secs 3` n'a pas été atteint.

**Mode `locked-prompt`** : collection verrouillée, `Unlock` renvoie une invite à laquelle personne ne répond (le faux service n'envoie jamais `Completed`).

| Commande | stdout (copié) | Code | Durée |
|---|---|---|---|
| `status` | `Trousseau verrouillé : déverrouillez le trousseau de la session, puis réessayez` | 4 | 12 ms |
| `resolve` | `TMDB : Trousseau verrouillé : …` | 4 | 8 ms |
| `raw-get` (sans garde) | `Trousseau indisponible : délai dépassé (8 s). Le trousseau est peut-être verrouillé et attend une confirmation (invite de déverrouillage non visible).` | 1 | 8007 ms |
| `resolve` avec env | `TMDB : configurée (source : environnement, verrouillé par l'environnement)` | 0 | 6 ms |

Journal du faux service pendant `raw-get` : `Unlock ['/org/freedesktop/secrets/collection/login/1'] -> returns prompt, nobody will answer it`, puis `Prompt called; no Completed signal will be sent`. Pendant `status`, seuls `OpenSession`, `ReadAlias` et `Properties.Get(Locked)` ont été reçus : **aucune invite n'a été envoyée**.

Résultat : le délai de 8 s du spike borne bien l'attente d'invite (sans lui, la crate attendrait environ un an). La garde évite le cas dans le parcours normal.

Mécanique du délai : le thread de l'appel reste bloqué après l'expiration. Le spike est un CLI qui se termine juste après, donc ce n'est pas un problème ici. Dans l'application, voir la recommandation 4.

## 7. Recommandations pour `SecretStore` (EPIC 03)

1. **Écriture seule.** Exposer `configured`, la source (`env` ou `trousseau`), l'état `locked` et jamais la valeur (ARCHITECTURE.md §9). `set` et `clear` sont les seules opérations d'écriture.
2. **Ordre de résolution.** Lire `OPEN_MOSAIK_TMDB_API_KEY` en premier. Si elle est définie et non vide, ne pas accéder au trousseau et afficher le réglage comme verrouillé par l'environnement. C'est le seul cas qui fonctionne sans Secret Service (scénarios 2a, 2b, 3, 4).
3. **Garde de verrouillage avant tout accès.** Lire `Properties.Get(org.freedesktop.Secret.Collection, Locked)` avant `get` ou `set`. Ne jamais appeler `get_password` sur une collection verrouillée depuis un chemin d'interface : cela envoie `Unlock`, et l'invite peut attendre sans borne (section 4).
4. **Délai.** Exécuter chaque appel au trousseau dans un thread de travail avec un budget de 8 s (valeur testée). Ne jamais bloquer le thread UI. Le thread expiré reste bloqué jusqu'à la fin de l'appel. Pour l'application, prévoir un pool borné, ou accepter ce coût si les appels sont rares.
5. **Messages (français, textes exacts du spike).**
   - `Trousseau indisponible : <raison>` : service absent, bus invalide, délai dépassé, refus. La raison est la chaîne d'erreur brute, pour le diagnostic.
   - `Trousseau verrouillé : déverrouillez le trousseau de la session, puis réessayez`.
   - `TMDB : configurée (source : environnement, verrouillé par l'environnement)`.
   - `TMDB : non configurée`.
   - « Aucune valeur enregistrée dans le trousseau » reste un message interne : ne pas l'afficher, traiter comme « non configurée ».
6. **UI « verrouillé ».** Trois états distincts, sans afficher de valeur :
   - *verrouillé par l'environnement* : champ désactivé, `set` et `clear` refusés, indication de la variable ;
   - *trousseau verrouillé* : bouton « Réessayer » et texte de la recommandation 5 ;
   - *trousseau indisponible* : message de la recommandation 5, saisie refusée avec la raison, et rappel que la variable d'environnement reste possible.
7. **Écriture.** `set` vérifie `Locked` puis écrit. En cas de verrou, il renvoie l'erreur sans rien conserver en mémoire. Le test avant enregistrement (`MetadataProvider::check`) reste indépendant du trousseau.
8. **Transport.** Évaluer la feature `crypto-rust` de `keyring` pour chiffrer le secret sur le bus (échange Diffie-Hellman). **Non testé dans ce spike** : à valider avant d'enregistrer une clé.
9. **Dépendance directe.** `dbus-secret-service` est nécessaire pour lire `Locked`, que `keyring` n'expose pas. Garder la même version que celle de `keyring`.

## 8. À confirmer manuellement

Ces points ne peuvent pas être automatisés dans un bus isolé sans bureau.

- **M1. Invite graphique réelle.** Sur une session GNOME de test uniquement, verrouiller le trousseau de connexion (par exemple avec Seahorse, ou avec `Service.Lock` comme dans le scénario 3), puis lancer :
  `secret-service-spike --timeout-secs 60 raw-get`.
  Attendu : une fenêtre d'invite apparaît et la commande attend.
  - Ne pas répondre : attendu `délai dépassé (60 s)` avec le code 1.
  - Annuler l'invite : attendu `unlock prompt was dismissed` avec le code 1.
  - Saisir le mot de passe : attendu la valeur enregistrée.
- **M2. Autologin.** Sur une machine avec connexion automatique : après redémarrage, vérifier l'état du trousseau de connexion :
  `dbus-send --session --print-reply --dest=org.freedesktop.secrets /org/freedesktop/secrets/collection/login org.freedesktop.DBus.Properties.Get string:org.freedesktop.Secret.Collection string:Locked`.
  Attendu si le trousseau a un mot de passe : une réponse contenant `true`. **Format exact non observé.** Cette commande ne demande aucune invite.
- **M3. KWallet.** Non testé. Vérifier si KWallet expose `org.freedesktop.secrets` et le même comportement de verrouillage.
- **M4. Machine sans trousseau.** Le scénario 2a simule une absence de service. Vérifier sur une installation minimale sans `gnome-keyring` que le message est identique.
