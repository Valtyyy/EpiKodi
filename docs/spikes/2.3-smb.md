Code et scripts : `spikes/smb/` (voir son `README.md` pour tout rejouer).

| Rust | rustc 1.99.1 |

## 3. Pannes et partage lent

Methode : `scripts/outage.sh` (client lance en arriere-plan, panne injectee apres 4 s, delai mesure depuis l'injection jusqu'a la sortie du client) ; listage avec 300 ms de pause par dossier, lecture sequentielle par blocs de 64 KiB + 20 ms de pause.

### 3.1 Temps jusqu'a l'erreur

| Panne | Operation | Timeout client | Delai | Erreur |
|---|---|---|---|---|
| `docker stop` | listage recursif | aucun | 0.19 s | `ConnectionStopped` |
| `docker stop` | listage recursif | 3 s | 0.20 s | `ConnectionStopped` |
| `docker stop` | lecture longue | aucun | 0.16 s | `IoError: Message processing failed. Failed to send message to worker!` |
| `docker pause` | listage recursif | aucun | **10.00 s** | `OperationTimeout(ReceiveNextMessage, 10s)` (timeout interne de la crate, defaut 10 s) |
| `docker pause` | lecture longue | aucun | **10.04 s** | `IoError ... Operation timed out: ReceiveNextMessage, took >10s` |
| `docker pause` | listage recursif | `tokio::time::timeout` 3 s | 3.01 s | `CLIENT TIMEOUT` |
| `docker pause` | lecture longue | `tokio::time::timeout` 3 s | 3.01 s | `CLIENT TIMEOUT` |
| `docker pause` | lecture longue | `ConnectionConfig::timeout` = 2 s | 2.01 s | `Operation timed out: ReceiveNextMessage, took >2s` |
| `docker pause` | **connexion** (`share_connect`) | aucun | **> 120 s** (tue par `timeout 120`) | aucune erreur : bloque indefiniment |
| `docker pause` | **connexion** | `ConnectionConfig::timeout` = 2 s | **> 120 s** | idem : le timeout de la crate ne couvre PAS la connexion |
| `docker pause` | connexion | `tokio::time::timeout` 3 s | 3.01 s | `CLIENT TIMEOUT` |
| `docker stop` | connexion | aucun | 0.005 s | `Transport error: Connection refused (os error 111)` |

Lecture : un arret (`stop`) est detecte immediatement (RST/FIN). Un serveur gele (`pause`, equivalent d'un cable debranche ou d'un firewall en DROP) n'est detecte qu'apres 10 s par la crate (reglable via `ConnectionConfig::timeout`), et **jamais** a la phase de connexion/negociation : il faut un `tokio::time::timeout` externe.

### 3.2 Partage lent (`tc qdisc add dev eth0 root netem delay 300ms`, cote serveur)

| Mesure | Sans delai | Avec +300 ms |
|---|---|---|
| Connexion + auth | 0.18 s | 1.81 s |
| Listage recursif (54 dossiers) | 9.15 s | 66.19 s |
| 10 `read_at` de <= 64 KiB | non mesure | 3.61 s (~360 ms / lecture), 10/10 identiques |
| Debit sequentiel, blocs de 1 MiB | 24.5 MB/s | 3.1 MB/s (`52428800 bytes in 16.92s`) |

### 3.3 Recuperation (`scripts/recovery.sh`, panne a t=5 s, levee a t=20 s, un seul `Client`)

- `pause` 15 s : une lecture en cours a bloque 4.04 s puis a abouti (`old_handle=OK(4096) (4.04s)`), l'ouverture d'un nouveau handle sur le meme client fonctionne ensuite (`OK(4096) (82.70ms)`), puis retour a la normale (42 ms / 125 ms). Seul le `close()` lance pendant la pause a attendu 10.09 s (erreur ignoree par le spike). **Le client survit a une pause plus courte que le timeout interne.**
- `stop` puis `start` : `old_handle=ERR ... Failed to send message to worker!` et `create_file ERR` sur le meme client pendant toute la fin du test (50 s) ; avec `--reconnect`, `Connection refused` tant que Samba est arrete, puis `>>> NEW CLIENT connected OK` a t=20.8 s. **Il faut construire un nouveau `Client`.** Les erreurs de l'ancien client sont instantanees (~50 microsecondes), donc le disjoncteur n'attend rien.

## 4. Limites observees de `smb` 0.12.1

1. **Invite fragile** : exige `allow_unsigned_guest_access: true` et le nom d'utilisateur litteral `/GUEST` ; tous les autres noms essayes echouent avec une `InvalidState` peu parlante (voir section 2). A figer dans un test d'integration.
2. **Pas de timeout a la connexion** : `share_connect` vers un hote gele ne retourne jamais, meme avec `ConnectionConfig::timeout` (>120 s observes).
3. **Timeout par defaut de 10 s** pour toute requete en vol (`ReceiveNextMessage`), reglable mais global a la connexion.
4. **Client definitivement casse apres coupure TCP** : pas de reconnexion automatique.
5. **Latence fixe d'environ 40 ms par aller-retour, meme en local** : lecture par blocs de 64 KiB = 1.6 MB/s (`52428800 bytes in 33.47s`) contre 24.5 MB/s avec des blocs de 1 MiB ; ouverture d'un handle ~125 ms, listage ~170 ms par dossier. Hypothese non verifiee : Nagle / ACK retarde, `set_nodelay` etant absent des sources de `smb` et `smb-transport` (`grep -i nodelay` vide). Consequence : lire par gros blocs (>= 1 MiB) et eviter le listage dossier par dossier en serie (parallelisme limite).
6. API de bas niveau : `create_file` renvoie `Resource::{File,Directory}`, le listage passe par `Directory::query::<FileDirectoryInformation>` (crate `smb-fscc`), chemins avec `\`. Un `read_at` peut etre court (non observe ici : `got == asked` sur toutes les lectures).
7. Un `close()` sur serveur gele bloque aussi 10 s ; ne pas l'attendre dans le chemin critique.

## 5. Evaluation de `pavao` (fallback)

Execute reellement : conteneur `rust:1-bookworm` + `libsmbclient-dev`, `pavao` 0.2.16, meme reseau Docker que Samba (`spikes/smb/pavao/`).

```
list_dir /Movies -> 4 entries in 23.442443ms: ["C", "A", "big", "B"]
read 65536 bytes at offset 12345678, first 8 = [ba, b4, 9b, 7e, 5b, 70, ee, 63]
```
Les 8 octets correspondent au fixture (`dd ... | xxd -p` -> `bab49b7e5b70ee63`). Compilation et execution a la premiere tentative (~5 s de compilation apres l'installation des paquets). Contre un serveur gele (`docker pause`) : `list_dir: BadFileDescriptor` (panic du test) apres ~20 s (delai conteneur compris), donc plus lent que `smb` + timeout 3 s. Non teste : invite, mauvais mot de passe, `netem`.

Lecture du code source (0.2.16, `src/smb/client.rs`) : le contexte libsmbclient est un `static SMBCTX: Arc<Mutex<SmbContext>>` unique pour tout le processus ; le mutex n'est pris que le temps de recuperer le pointeur (`ctx()`), l'appel libsmbclient se fait hors verrou, mais le contexte `SMBCCTX` reste partage par tous les clients et les options ne sont appliquees qu'a sa creation. Le verrou global decrit par la doc n'a donc **pas** ete reproduit comme un blocage d'un partage par un autre (non teste en concurrence). API synchrone et bloquante : il faudrait `spawn_blocking`, et un appel bloque occupe un thread jusqu'au timeout de libsmbclient (~20 s observes).

Conception de repli, non implementee : un processus de travail dedie par source (binaire `smb-worker` lance par `infra`, un seul `SmbClient` pavao par processus, protocole JSON-lines ou `postcard` sur stdin/stdout : `list(path)`, `read_at(path, off, len)`, `health`). Le verrou / contexte global est ainsi confine par partage ; un worker bloque est tue (PID connu) et relance sans toucher aux autres sources. Cout : un processus par source, copie memoire des blocs, dependance systeme `libsmbclient` a packager.

## 6. Verdict

**Garder `smb` 0.12.** Listage recursif, `read_at` exact, NTLM, invite (avec la reserve `/GUEST`), erreurs d'authentification explicites : tout est OK sur Samba 4.17. Les defauts (pas de timeout de connexion, pas de reconnexion, latence de 40 ms par requete) se contournent dans `infra`, sans changer le port `SourceProvider`. `pavao` reste le plan B (processus de travail), non necessaire a ce stade. Limite de la validation : un seul serveur (Samba), pas de test Windows/NAS, SMB sans chiffrement force, pas de test de signature obligatoire.

## 7. Recommandations pour le `SourceProvider` SMB

- **Timeouts a poser avec `tokio::time::timeout`** (la crate n'en pose aucun a la connexion) : connexion + auth 5 s ; ouverture/listage d'un dossier 5 s ; `read_at` 5 s (augmenter si blocs > 1 MiB sur lien lent) ; `close()` 2 s ou en tache detachee. En complement, `ConnectionConfig::timeout` = 5 s pour les requetes en vol.
- **Recreer le `Client`** a la premiere erreur de type `ConnectionStopped`, `Failed to send message to worker`, `OperationTimeout` ou `Connection refused` ; ne jamais reutiliser un client en erreur. Une erreur `Logon Failure` / `Access Denied` n'est pas une panne reseau : ne pas la compter dans le disjoncteur, remonter "identifiants refuses".
- **Disjoncteur** : `Unreachable` apres 3 echecs reseau consecutifs (ou 2 timeouts de 5 s) ; en `Unreachable`, aucune requete distante, sonde de sante toutes les 15-30 s avec le meme timeout de connexion de 5 s ; retour `Online` apres 1 sonde reussie (connexion + listage de la racine).
- **Seuil `Slow`** : latence mediane d'une operation courante (ouverture + petite lecture) > 1 s, ou ouverture/auth > 2 s sur 3 mesures glissantes (reference mesuree : 0.18 s de connexion et ~125 ms par ouverture a 0 ms de delai ; 1.8 s et ~660 ms a +300 ms). Retour `Online` sous 500 ms.
- **Debit** : lire par blocs >= 1 MiB dans la passerelle `Range` (64 KiB donne 1.6 MB/s, 1 MiB donne 24.5 MB/s) ; limiter le nombre de dossiers listes en parallele pour ne pas saturer le serveur.
- **Scan** : un listage de 54 dossiers prend 9 s sur loopback et 66 s a +300 ms ; le scan doit etre incremental, annulable et ne jamais bloquer l'UI (donnees toujours servies depuis SQLite, C6).
- **Invite** : coder en dur `/GUEST` + `allow_unsigned_guest_access` pour les partages sans identifiants, avec un test d'integration Samba en CI.
